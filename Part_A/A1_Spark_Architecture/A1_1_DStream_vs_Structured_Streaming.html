From batch processing to streaming

How Spark processes a stream, and how DStreams and Structured Streaming describe the work

01

Introduction

Data processing often begins with a collection that has already been gathered. A shop, for example, can collect all its sales during the day and calculate the total after closing. The records form a finished group, and the calculation runs over that group. This is batch processing. It is useful when a result can wait until a chosen time, such as a daily sales report.

Now suppose the shop owner wants to see the sales total change throughout the day. A calculation that runs only at closing time cannot provide those updates. The system needs to keep accepting new sales and updating its answer while the business is still operating. Each new sale is an event, and the continuing flow of events is a data stream.

Stream processing means performing calculations on this continuing flow. The calculation stays active and deals with new data as it becomes available. The connection with batch processing is that a streaming engine can repeatedly process small groups of new records. These small groups are called micro-batches. Instead of waiting for the whole day’s records, it can work through short intervals and produce results throughout the day.

This leads to an important question: how can a system process an input that keeps growing? Spark provides two ways to describe that work. Understanding them first requires a brief look at what Spark does with a collection of data.

02

How Spark processes data

Spark Streaming is an extension of the core Spark API that enables scalable, high-throughput, fault-tolerant stream processing of live data streams. Data can be ingested from many sources like Kafka, Kinesis, or TCP sockets, and can be processed using complex algorithms expressed with high-level functions like map, reduce, join and window. Finally, processed data can be pushed out to filesystems, databases, and live dashboards. In fact, you can apply Spark’s machine learning and graph processing algorithms on data streams. Spark guide

Internally, Spark Streaming divides the incoming flow into small batches. The Spark engine processes each batch and produces another batch of results, as shown below.

A small batch does not mean that all of its records are processed one after another on a single machine. Spark can still divide that batch into smaller pieces called partitions and process them in parallel. Batching determines which records are handled together; parallel execution determines how the work on those records is shared.

The two streaming models below use this processing engine differently at the programming level. DStreams present the input as a sequence of distributed collections. Structured Streaming presents it as a table receiving new rows.

3.1 DStreams

A stream represented as a sequence of RDDs

A DStream is a discretized stream. “Discretized” means that a continuing flow has been divided into separate intervals. With a one-second batch interval, one collection contains the records received during one second, another contains the next second’s records, and the sequence continues.

Each collection is an RDD, short for Resilient Distributed Dataset. “Dataset” means a collection of records. “Distributed” means its pieces can be processed across different worker processes, called executors. “Resilient” refers to Spark’s ability to reconstruct lost pieces when the required input remains available. An RDD is immutable: operations create new RDDs instead of changing the original collection.

When an operation is applied to a DStream, Spark applies corresponding operations to its RDDs. For word counting, the first operation splits each incoming line into separate words. In the next illustration, every collection of lines produces a corresponding collection of words.

Example code

The following Python code follows the guide’s basic word-count example. It reads text through a socket, a connection through which another program sends text. Here, localhost means the same computer and 9999 identifies the connection’s port. These details describe where the text comes from; the counting logic begins after it has been received.

dstream_word_count.py
from pyspark import SparkContext
from pyspark.streaming import StreamingContext

sc = SparkContext("local[2]", "DStreamWordCount")
sc.setLogLevel("ERROR")

# Collect incoming lines into one-second batches.
ssc = StreamingContext(sc, 1)
lines = ssc.socketTextStream("localhost", 9999)

# One line can contain several words.
words = lines.flatMap(lambda line: line.split(" "))

# Give every occurrence a 1, then add the 1s for each word.
pairs = words.map(lambda word: (word, 1))
word_counts = pairs.reduceByKey(lambda left, right: left + right)

# Print the counts calculated for each batch.
word_counts.pprint()
ssc.start()
ssc.awaitTermination()

SparkContext sets up the application’s connection to Spark. StreamingContext(sc, 1) adds streaming with one-second batches. local[2] gives this local application two execution threads, allowing the socket receiver and processing work to run. The remaining operations form a short calculation:

  1. Split the lines. flatMap turns one line into several records. The line cat dog becomes the two words cat and dog.
  2. Mark each occurrence. map changes each word into a pair such as ("dog", 1). The 1 means “one occurrence”.
  3. Add matching occurrences. reduceByKey adds the values belonging to the same word within that batch. Three ("dog", 1) pairs produce ("dog", 3).
  4. Start and display. pprint() requests console output, start() starts processing, and awaitTermination() keeps the application running.

The catch with DStreams

The word-count example is short, but a complete streaming pipeline brings two practical difficulties.

Difficult to coordinate reliable processing. A pipeline may need to handle events that arrive late, recover after failures, and provide an exactly-once guarantee: each event must affect the final result once, including after retries. Spark Streaming provides recovery mechanisms, but developers still have to coordinate the input source, saved state, and output writes correctly. These requirements are achievable with DStreams; putting them together can require extra code, configuration, and testing.

Inconsistent batch and streaming interfaces. Batch processing can use RDDs or the DataFrame/Dataset interfaces, while legacy stream processing introduces the separate DStream interface. DStreams reuse many RDD operations, so the two are related, but developers still have to work with different abstractions when combining batch and streaming calculations. Sharing logic and maintaining the application becomes easier when both can be expressed through a common set of operations.

This raises the next question naturally: can we describe the overall answer as a table, and ask Spark to keep that answer up to date as more words arrive?

3.2 Structured Streaming

A stream represented as a table receiving new rows

Structured Streaming uses a different programming model. Each arriving record is treated as a new row in an input table. A query describes the answer to calculate from that input, and Spark maintains a result table as more rows arrive.

A query is simply a request for a calculation, such as “group the words by name and count them”. The input table is called unbounded because there is no fixed final row: the stream can continue. This makes the calculation resemble one over an ordinary, finished table, while Spark handles the continuing updates.

In Python, these tables are represented by DataFrames. A DataFrame organizes data into named columns, much like a spreadsheet. In this example the incoming text has one column named value. Splitting that text creates a table with one word in each row, and the result table contains a word column and a count column.

Example code

This code follows the Structured Streaming guide’s word-count example, using the same socket input as the DStream program. A trigger controls when another update is attempted. Here it requests an update every second.

structured_word_count.py
from pyspark.sql import SparkSession
from pyspark.sql.functions import explode, split

spark = (SparkSession.builder
         .master("local[2]")
         .appName("StructuredWordCount")
         .getOrCreate())
spark.sparkContext.setLogLevel("ERROR")

lines = (spark.readStream
         .format("socket")
         .option("host", "localhost")
         .option("port", 9999)
         .load())

# Put each word into a separate row named "word".
words = lines.select(explode(split(lines.value, " ")).alias("word"))

# Maintain a running count for every word.
word_counts = words.groupBy("word").count()

query = (word_counts.writeStream
         .outputMode("complete")
         .format("console")
         .trigger(processingTime="1 second")
         .start())

query.awaitTermination()

SparkSession provides the starting point for working with DataFrames. readStream defines a continuing input. After that, the calculation is:

  1. Split each line. split turns cat dog into a list containing cat and dog.
  2. Make one row per word. explode takes the items out of that list and places them in separate rows. alias("word") gives their column a name.
  3. Describe the result. groupBy("word").count() requests one count for every distinct word. Spark keeps those counts as new input is processed.
  4. Choose the output. writeStream defines how results are written. Complete mode prints the entire current result table after an update. start() starts the query.

The guide’s original illustration shows this same sequence. Read each vertical column as a later point in the calculation: the yellow records are input, and the green rows are the current word counts.

The information retained between updates is called state. For this calculation it includes the current count for each word. The picture shows the input table growing to explain the model, but Spark does not need to keep every original line forever. It can process new rows and retain the intermediate information needed to update the counts.

Structured Streaming normally executes these updates using micro-batches. A trigger controls when another update is attempted. Therefore, a continuously maintained table does not imply that each individual record is always processed in a separate job. In the example, the trigger requests a new micro-batch every second; the actual output time also includes the work needed to process and print it.

Running either word-count example

Use an environment with PySpark 3.5.7 and a compatible Java installation. The guides use Netcat to send text. Start nc -lk 9999 in one terminal, then run one Python file in another terminal with spark-submit dstream_word_count.py or spark-submit structured_word_count.py. Restart the connection and run the other program separately to compare them.

Type the first group’s lines, wait for their counts, then send the next group. A line placed in a different processing batch can change the grouping of the DStream output. Socket input and console output are learning examples; they do not provide durable end-to-end recovery.

3.3 What changes between the two models

The examples make the programming difference visible. DStreams expose a sequence of distributed collections and operations over them. Structured Streaming exposes an input table and a query whose result is maintained over time. That difference also affects how time, optimization, and recovery are expressed.

Time windows and late data

A running total answers “How many have arrived since the calculation started?” Sometimes the question is “How many happened during a particular period?” A time window is that period. A ten-minute window could cover 12:00 to 12:10. A five-minute slide starts another window at 12:05, so the windows overlap.

DStreams can combine the RDDs falling inside a window of batch intervals. The window length controls how much batch history is included, and the slide interval controls how often the window moves. Both must be multiples of the original batch interval. This is a window over the batches being collected and processed.

Structured Streaming can instead group rows using a timestamp inside each record. This is event time: when the event actually happened. It can differ from processing time, when Spark handles the record. Event-time windows are useful when a delayed record should still belong to the period when it was created. With overlapping ten-minute windows starting five minutes apart, a word created at 12:07 belongs to both 12:00–12:10 and 12:05–12:15.

For example, the guide shows a dog event created at 12:04 but received at 12:11. Its event time belongs to the 12:00–12:10 window. If the corresponding state is still retained, Structured Streaming can update that earlier count when the delayed record arrives.

Spark cannot retain every old window indefinitely. A watermark helps a supported event-time operation decide when to finish old windows and remove their state. The lateness allowance is measured against progress in the event timestamps, not a countdown on the computer’s clock. Events within the configured allowance are protected from being dropped because they are late; older events are not guaranteed to be included. DStreams can implement event-time policies too, but their standard batch-window operations do not provide Structured Streaming’s watermark mechanism.

Data structure and engine optimization

An RDD can hold records in a form chosen by the programmer, and DStream code commonly uses functions that work directly on those records. A DataFrame describes named columns and their types. That description is its schema: for example, a word is text and a count is a whole number.

Structured Streaming builds on the Spark SQL engine. SQL is a language for expressing queries over tables; this engine also runs calculations described through Python DataFrame operations. Built-in column operations give Spark information it can use to plan the work efficiently. Its query optimizer, called Catalyst, can rearrange supported operations and avoid unnecessary work. The engine also uses efficient execution techniques for supported expressions. Spark cannot understand an arbitrary user-written function to the same degree, so neither model guarantees better performance for every possible program.

The same DataFrame grouping expression can often be used on a completed dataset and on a stream. Streaming adds requirements such as keeping state and deciding when to publish updates. Some ordinary batch operations are restricted on a continuing input: for example, asking for a final sort of all records makes little sense when more records can always arrive.

State and what gets written out

The difference between the two word-count outputs comes from their calculations. The DStream example asks for separate batch counts. The Structured Streaming example asks for a maintained total. DStreams also support running state; Structured Streaming also supports operations that simply pass through new rows. Choosing a model and choosing a particular calculation are separate decisions.

Structured Streaming makes the output contract explicit through three modes. Complete writes the whole current result, as in the example. Update writes the rows changed by the latest update. Append writes new result rows that will not later change under that query’s rules. The valid choices depend on the query and destination; a running word count cannot simply use Append mode to publish permanently final counts while more occurrences can still arrive.

Failures and saved progress

A checkpoint saves progress and information needed to continue a calculation. For a running count, this can include the saved counts and the input positions already handled. DStreams use RDD recovery and checkpointing, with input recovery depending on the chosen source. Structured Streaming coordinates query progress, state, and supported output commits.

Both need the complete path to be considered. A source must make the required input available again after failure, and a destination must deal correctly with retries. This is why “exactly once” does not mean that every arbitrary action inside any streaming program automatically happens once. The guides’ socket-and-console examples explain the computation; they are not examples of durable end-to-end delivery.

For a new application, Structured Streaming is usually the starting point recommended by Apache. Its main advantage for the programmer is that a continuing calculation can be expressed as a table query, while Spark manages the supported incremental updates. DStreams remain useful for understanding and maintaining applications built around the earlier RDD-based model.
